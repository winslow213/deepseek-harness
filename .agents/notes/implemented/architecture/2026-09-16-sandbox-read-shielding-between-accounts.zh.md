# Agent Note：同机多账号之间的读隔离

Status: implemented

[English](2026-09-16-sandbox-read-shielding-between-accounts.md) | 中文

## Problem

把多个租户放在同一台机器上，意味着它们的数据共享同一个父目录。团队 shell 部署里，每个账号的 home 都位于同一个用户根目录下（`/home/winslow/.dsh-users/<account>`），各自持有一个 `.credentials.yaml`，里面是该账号的 LLM API key 和浏览器会话授权密钥，此外还有会话日志和私有 workspace。所有账号都以同一个 OS 用户运行，因此内核层面它们之间根本没有任何边界。

沙箱也没能提供这个边界，因为它从来没被要求提供。`SandboxMode` 限定的是**文件系统效果**，三种模式（`read-only`、`workspace-write`、`danger-full-access`）描述的都是命令可以*修改*什么。bwrap profile 把宿主根只读挂载（`--ro-bind / /`），Landlock 授予 `readOnly: ['/']`，Seatbelt 以 `(allow default)` 开场——每一种都是对"只管写"策略的准确表达，每一种都让宿主上所有可读文件继续可读。在部署主机上实测：一个账号里被沙箱限制的 `bash` 可以明文读取兄弟账号的 `.credentials.yaml`，24 个非本人账号全部可以这样读。

这才是这个缺陷值得被点名的形态：**写限制不等于读隔离**，而一个采用了前者却以为两者都有的部署，在它自以为有边界的地方其实什么边界都没有。

## Decision

**为沙箱策略新增一个可选的读边界，表达为"被拒绝的根 + 重新暴露的子树"，并让每个后端从同一个共享 helper 推导各自的写法。**

`SandboxExecutionPolicy` 新增 `readDeniedRoots` 和 `readAllowedRoots`。被拒绝的根连同它的整棵子树一起被隐藏；位于其中的允许根会被重新暴露，这正是让账号自己的 home 继续可用、同时隐藏其兄弟账号的方式。两者都是 `sandbox-policy` 上的部署配置，默认不存在——未启用遮蔽的部署保持原有的"任意可读"语义，因此单租户主机不受影响。

`dsh-sandbox` 的 `roots.ts` 里的 `readShield(policy)` 是这个含义的唯一归属，正如 `writableRoots()` 是写侧的唯一归属：它规范化两个列表，丢弃位于所有被拒绝根之外的允许根（重新暴露一个本来就没被隐藏的路径，等于放宽调用方从未要求放宽的读），并拒绝把 `/` 设为被拒绝根（没有任何重新暴露能让它可用）。每个后端翻译同一组结果：

- **bwrap** 在每个被拒绝根上挂一个 `tmpfs`，用 `--dir` 重建中间目录，再把允许的子树 `--ro-bind` 回来，**并且要在该模式自身的挂载之前**。挂载顺序在两个方向上都是关键：遮蔽必须早于重新绑定，而位于被拒绝根内部的可写 workspace 必须在遮蔽之后才绑定，否则那次只读重新暴露会悄悄把它变成只读。
- **Seatbelt** 依次追加 `(deny file-read* (subpath …))` 和 `(allow file-read* (subpath …))`，因为 Seatbelt 取最后一条匹配的规则。
- **Landlock** 把它那句一刀切的 `readOnly: ['/']` 换成"系统路径白名单 + 重新暴露的子树"，但**仅在存在遮蔽时**这么做——Landlock 是白名单语言，无法从一刀切授权中减掉某个路径，因此未启用遮蔽的部署保持今天的写法。

**团队 shell 部署隐藏用户根目录，并重新暴露账号自己的 home。** 注入的 `sandbox-policy` patch 从环境变量（`DSH_USERS_ROOT` 和 `DSH_HOME`）读取两者，而不是写死任何路径，因此目录布局仍然是一个部署选择。

## Alternatives considered

**每个账号一个 OS 用户，各自带 systemd unit、端口和反向代理路由。** 被账号所有者否决：25 个账号意味着 25 套系统用户、服务和端口，对这个部署来说维护成本不可接受。它也并非没有代价——24 个非本人账号目录是 `drwxrwxr-x`，所以这条路线还需要对每个目录（包括每个 `workspace/`）执行 `chmod 700`，内核才愿意隐藏任何东西。记录在此是因为它技术上是干净的选择，并且以后还会被提出来；其中每租户容器/microVM 的变体才是可以自动化的版本。

**只修 `read` 工具已有的栅栏（`region-router.ts`）。** 否决为不充分：那道栅栏只覆盖 `FsProvider` 路径。被限制的 `bash` 通过子进程同样能读到这些文件，`grep`/`glob` 工具也能，而且它们走的是完全未受限的裸 `ctx.subprocess.spawn`。四条读通道里有三条绕过了 `FsProvider` 栅栏，因此只修栅栏会让报告出来的洞继续敞着。

**只拒绝读、不重新暴露账号自己的 home。** 否决：那样遮蔽也会连带隐藏账号自身工具需要加载的文件，于是每条被限制的命令都会失败，而不是被隔离。

## Consequences

账号之间的读隔离现在表达在沙箱策略自身，并由已经在执行写限制的同一批后端执行；已针对真实挂载验证：被遮蔽的命令无法列出兄弟账号目录（连名字都不出现）、无法在其 `.credentials.yaml` 未遮蔽时可读的情况下读取它、通过遮蔽仍能读自己的 home、在 workspace 位于被拒绝根内部的情况下仍能写它、并且 `bash`/`node`/`git` 仍然可用。`readShield()` 有单测覆盖规范化、允许根在拒绝根内部、位于所有拒绝根之外的丢弃、对 `/` 的拒绝、以及前缀形兄弟路径的处理；挂载行为由 `bwrap.e2e.ts` 中四个新增用例覆盖。

**这是应用层 containment，不是内核边界。** 所有进程仍以同一个 OS 用户运行，因此它能挡住租户 agent 通过所提供的工具触达同伴（即被报告的威胁），但挡不住绕过沙箱 seam 直接 spawn 的插件、`danger-full-access` 模式下的会话、宿主进程自身，或任何不查询 `ctx.sandbox` 的代码路径。敌意租户的威胁模型需要容器或 microVM。

**Landlock 在本机未做 e2e 验证。** 开发检出里缺少 `landlock-run` 静态启动器（平台包只带了 Node-API 的 flock addon），因此本机生效的是 bwrap 这一档；Landlock 的授权推导有单测覆盖，运行时证明由 CI 里的 `landlock.e2e.ts` 负责。收窄它的系统白名单是本次改动中唯一可能把一个能用的 shell 弄坏的部分，因此它被限制在启用遮蔽的场景里，并由自己的测试套件覆盖。

**`grep`/`glob` 的搜索通过同一个 seam 受限。** 这些工具通过裸 `ctx.subprocess.spawn` 启动 ripgrep，因此 `rg` 是代表工具去读文件、完全没有任何沙箱——这是四条读通道里的第三条，也是只修沙箱会漏掉的那条。`runRipgrep` 现在用调用会话的策略把它的 argv 包进 `ctx.sandbox`，于是搜索工具和 `bash` 对"某个会话能读哪里"的判断一致。这两个服务是可选读取（`ctx.get`）而不是注入：搜索文件本身并不需要沙箱栈，而且存在挂载了这些工具却没有任何 provider 的组合，硬依赖会让它们加载不了。当沙箱**确实**挂载时，受限就不是可选项——策略会被应用，而一个无法完成限制的 runner 会让搜索失败，而不是退回未受限的 `rg`。

**轮换已泄露的凭据不在本次范围内，但仍然必须做。** 关闭读通道不会让一个已经泄露出去的 key 重新变成秘密。
