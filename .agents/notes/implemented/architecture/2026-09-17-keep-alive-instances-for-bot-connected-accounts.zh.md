# Agent Note: Keep-alive instances for accounts with a bound IM bot

Status: implemented

[English](2026-09-17-keep-alive-instances-for-bot-connected-accounts.md) | 中文

## Problem

实例正是成员的 IM 机器人所对话的对象：机器人的 agent、工作区与会话都活在实例里。实例只在登录时启动（`handleLogin` → `lifecycle.ensure`），且每一个实例都随生成它的账户服务一同消亡。因此，一次为更新代码而做的停机重启会让所有机器人下线，并且在每位成员碰巧打开 Web UI 之前，没有任何机制把它们带回来。

[空闲回收白名单](../feature/2026-09-16-idle-reclaim-whitelist.zh.md) 加入了 `idle_exempt`，让操作者能把某账户标记为"应当保持运行"，并由 `restoreKeptAlive` 在服务启动时重启这些账户。仍有两个缺口。

第一，该恢复只执行一次。启动之后因任何原因死掉的实例——崩溃、被 OOM 杀死、登出——都不会被重启，于是这个标志的承诺只维持到第一次故障为止。这是直接观察到的：`darcy` 被标记为豁免，其实例几分钟后死掉，账户此后一直冷着，机器人下线。

第二，`idle_exempt` 是一份手工名单。已连接机器人的账户本身就已经属于"必须保持运行"——没有实例，机器人就不可达——但操作者必须知道要把这件事另外复述成一个不相关的事实。`anders` 跑着微信机器人却从未被标记豁免，于是没有任何东西让它保持在线。

两种故障还都无法诊断。`spawnUserInstance` 把子进程的 stderr 累积到一个局部变量里，只在 30 秒内没出现 URL 时才打印，因此之后才退出的实例不会在日志中留下任何原因。

## Decision

**保活集合是 `idle_exempt` 与"已绑定 IM 机器人"的并集，每次扫描重新计算。**

`listBotConnectedUsers`（`shell/src/spawn-user.ts`）从磁盘而非数据库推导后半部分，因为机器人绑定归 `@xmanrui/dsh-im` 所有，它在账户服务的 schema 中没有行。它遍历每个账户 `integrations/` 下的每个目录，只要 `config.json` 或 `workspaces.json` 之一带有非空条目就视为已绑定机器人——两者都算，因为只有 `config.json` 覆盖"机器人注册于某个已结束的会话"，而只有 `workspaces.json` 覆盖"该检查不认识的配置布局"。机器人列表的发现方式是查找任意顶层非空数组或字符串值映射，而不是指名某个字段，因为各通道各自声明其配置类型（飞书是 `bots`，微信是 `accounts`），或者干脆不声明。

**`InstanceManager.keepAlive()` 跑在既有的 60 秒扫描上，并在服务启动时由同一实现调用。** 不新增第二个定时器：扫描本已为回收而存在，而这两半是同一个策略问题从相反方向各问一次。运行中的账户在咨询 `ensure` 之前就被跳过，因此稳态下每个账户只付一次存储查询且不产生日志噪音；而不得不启动的账户会在日志中被点名，因为重启才是值得看见的事件，否则它完全不可见。`server.ts` 在 `listen` 之后调用同一个方法，而非自己那份循环副本，于是"哪些账户必须在线"只有一个归属。

**空闲回收跳过保活集合，且两半读取同一份快照。** 没有这个跳过，一个必须保持在线但未被标记 `idle_exempt` 的账户——正是 `anders`——会在空闲超时时被回收并立刻重启，每个周期都掉一次机器人连接。这在生产中被复现：重启间隔与 30 分钟空闲阈值吻合。每轮只读一份 `Set` 也避免两半对同一账户产生分歧。

**保活集合不可读时整轮放弃，而不是当作空集。** 没有它就去回收，恰恰会回收这一轮本要保护的账户，也就是正在被修的故障。扫描记录日志后返回。

**`spawnUserInstance` 在子进程退出时打印捕获的 stderr**，并限制为末尾 8 KB，使长寿命实例不会无限增长该缓冲。干净停止（code 0、无信号）以 info 记录，其余以 error 记录。

## Alternatives considered

**保留 `idle_exempt` 作为唯一信号，并要求操作者把机器人账户也标记上。** 被否决：这让正确性依赖于操作者记得记录一个系统本就能观察到的事实。取并集意味着两个理由都不必被复述进对方的记账里，而显式标记账户的操作者依然得到他所要求的行为。

**为保活单独设一个看门狗定时器。** 被否决：扫描本就以该间隔运行，而第二个定时器会让两者在同一轮内对同一账户产生分歧——正是上面那个回收/重启循环的成因。

**把机器人连接记录进 `dsh_users` 以便查询可以 join。** 被否决：绑定是 IM 插件的数据，由插件在账户 home 下写入与重写。把它复制进账户 schema 会制造一份需要保持同步的第二副本，而账户服务里没有能拥有它的写入者。

**只把 `config.json` 当作机器人信号。** 被否决：它是本部署恰好查看过的字段，也是该通道自己的 schema。两个文件都读、不指名数组字段，意味着该检查对配置布局不同的通道依然有效。

**进程退出时就地重启实例，而不是靠扫描。** 被否决：它覆盖不了最要紧的情况——实例是因为整个账户服务死掉而死，此时已没有任何进程能去执行重启。

## Consequences

已连接机器人的账户实例现在能熬过任意长的服务生命周期，而不只是启动那一刻；一次服务重启会恢复所有已连接机器人的账户，无需任何人登录。本部署中恢复集从 5 个（仅 `idle_exempt`）变为 7 个，多出的两个是被发现的而非被配置的。

该策略现在每轮都从文件系统推导，比每账户读一个布尔量更费，且原则上可能因某个陈旧或手工构造的 `integrations/` 目录把一个账户提升为保活。替代方案是机器人静默不再应答，那是更糟的错误。诊断改动决定了"有东西重启了它"与带时间戳的原因之间的差别：生产环境里正是 `[spawn-user] anders exited 0 on port 32007 (no output)` 接着 `[team-account] started instance for anders (kept alive)` 这两行指出了回收循环。

测试覆盖为 `shell/tests/instance-manager-keepalive.spec.ts`，它通过覆写 `ensure`/`stop` 来检验策略而不启动任何进程，并针对一个一次性 users root 真实运行机器人扫描。它双向钉住并集、钉住防止回收循环的跳过、钉住同时具备两个理由的账户只启动一次、钉住未绑定机器人的集成目录被忽略，以及钉住集合不可读时不回收任何账户。
