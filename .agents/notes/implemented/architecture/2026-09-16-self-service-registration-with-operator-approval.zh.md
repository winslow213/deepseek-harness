# Agent Note：自助注册，由运营者审批放行

Status: implemented

[English](2026-09-16-self-service-registration-with-operator-approval.md) | 中文

## Problem

创建团队 shell 账号需要运营者登录主机执行 `account-cli create-user <username> <password>`。到 25 个账号这个量级，就是每来一个人打断一次；而且账号名是运营者手输的，很快就不再等于成员的邮箱地址。

公开注册表单是最直观的解法，也是最直观的风险。这套部署的入口主机在局域网内任何人可访问，因此"提交即创建账号"的表单等于把创建账号的权力交给每一个能解析到该地址的人——而这个账号正是通往一台持有团队 LLM key、私有 workspace 和 wiki 的实例的凭据。所以注册必须做成**先申请、后审批**，中间不存在任何账号。

第二个约束来自通知通道本身。账号服务跑在局域网主机上，飞书云端无法回调进来，所以交互式卡片上那个"批准"按钮——能让整个流程变成点两下的那个按钮——用不了。运营者能打开的审批链接，是唯一不需要入站可达性就能触达运营者的机制。

## Decision

**把注册拆成"无会话的申请"与"运营者的决策"，决策由一次性链接令牌授权。**

`GET /register` 由账号服务而不是代理渲染，这样"可受理域名列表"和"发放的密码"只有一个出处，页面上显示的就是真实生效的值。`POST /api/register` 把申请写入 `dsh_registrations`，从邮箱推导账号名，并向运营者发一条飞书消息。运营者做出决策之前，不创建任何东西。

账号名取邮箱 @ 前面的一段，转小写，把不能出现在 `DSH_HOME` 目录名里的字符替换为 `.`。这个名称同时就是 `user_id` 和 `DSH_USERS_ROOT` 下的目录，所以 `deriveUsername` 会拒绝一切无法作为安全路径分量的结果——以分隔符开头、归一化后为空、归一化后仍含 `..`——且申请人无法自行指定。

**审批一律走 POST，绝不走 GET。** 只认 GET 的审批链接，会被任何链接预取器、任何展开 URL 的聊天客户端、任何抓取邮件的扫描器批准；面对一条飞书通知，这不是假设性风险。`GET /approve?token=…` 只渲染决策页；`POST /api/approvals` 才消费令牌。令牌本身是 256 位，只以 SHA-256 哈希落库，绝不明文比对。

**令牌由那次决策消费，并与账号插入同处一个事务。** 一条条件式 `UPDATE … WHERE token_hash = $1 AND status = 'pending' … RETURNING *` 来认领该行；若没有匹配，说明申请已被决策或已过期。账号插入在同一事务中执行，因此重放、表单重复提交、或同一链接被并发批准，都不可能产生两个账号；而插入失败只会让申请保持待审批，不会白白烧掉运营者的链接。`decide` 正是按这一点覆盖测试的：同一令牌被并发批准两次，只创建一个账号。

**域名允许列表在通知之前校验，而不是之后。** `TEAM_REGISTRATION_DOMAINS`（逗号分隔，默认 `quectel.com`）在请求路径上校验，所以列表之外的地址根本到不了运营者的飞书——否则通知渠道就成了被刷的对象，而人成了限流器。

**通知失败是一种独立状态，而不是拒绝。** `notify_failed` 的行被排除在"每个邮箱、每个账号名各允许一条待审批申请"的部分唯一索引之外，因此申请人可以用同一邮箱重试；反过来先记 `pending` 再发送，则会把该地址锁死在一封没人看见的消息后面。没有飞书集成时服务仍会启动并只记录一条错误：为了一个现有 25 个账号都用不上的功能而拒绝启动，等于把登录也一起停掉。

**凭据取自运营者已有的 `dsh-feishu` 集成。** app id 与 owner open id 读自 `$DSH_USERS_ROOT/winslow/integrations/dsh-feishu/config.json`，app secret 通过 `.credentials.yaml` 中的 `secretRef` 解析，`TEAM_FEISHU_*` 可覆盖整个查找。服务本就以运营者身份运行，因此不需要任何新的授权；`.credentials.yaml` 的读取是对顶层 `refs:` map 的定点逐行扫描，而不是为账号服务引入一个它本来不需要的 YAML 依赖。

**改密码成了一个真正的 HTTP 面。** 审批发放的是共享默认密码（`TEAM_DEFAULT_PASSWORD`，`quectel@123`），每个被批准的成员都知道它，因此账号的私密性只到首次登录为止。`GET /password` 与 `POST /api/me/password` 在替换前会复核当前密码，所以光有一个被窃取的会话 cookie 无法接管账号。在此之前，改密码的唯一途径是运营者的 `account-cli reset-password`。

## Alternatives considered

**飞书交互式卡片的审批按钮 + webhook 回调。** 交互体验最好，但不可用：飞书云端够不到这个局域网内的地址，而为了拿到点两下审批就把账号服务暴露到公网，等于用一个仅限局域网的部署换来一个公开部署。记录在此，因为一旦入口主机以 TLS 对外发布，它就是正确的做法。

**只发通知，决策由 `account-cli` 完成。** 活动部件更少，也是运营者的次选。它输在频次上：这次改动的意义就在于加入团队不再需要主机权限，而 CLI 决策会把运营者每次拉回主机。

**用 GET 完成审批。** 链接最简单，被直接否决——理由见上。代价是多按一次按钮；收益是抓取通知 URL 不再是一项特权操作。

**账号名由表单字段决定。** 否决：这个名称是 `DSH_HOME` 目录和 `user_id`，让申请人自选意味着要校验一个任意的路径分量，并接受那些与运营者正在批准的邮箱不相符的名字。

**只要邮箱落在公司域名内就自动批准。** 运营者否决：域名只能证明邮件投递到了哪里，不能证明申请人有权拥有账号。

## Consequences

加入团队不再需要主机权限：申请人提交邮箱，运营者在飞书里批准，账号即以共享默认密码存在，成员随后到 `/password` 修改。`deriveUsername`、域名与邮箱校验、通知文案、凭据解析都有单元覆盖；申请、去重、重试、批准、拒绝、重放、并发、过期各路径跑在真实 schema 上——被测行为就是那条条件式 `UPDATE`、那些部分唯一索引和那个事务，用假的查询层根本练不到。

**审批链接的可达性受限于入口主机。** `TEAM_ENTRY_BASE_URL` 必须是运营者能从飞书点开的地址；默认是 `http://$DSH_ENTRY_HOST:3999`。不在公司网络里的手机端无法批准，而消息本身对此没有任何提示。

**注册与入口主机共用明文 HTTP。** 表单与审批链接除令牌外不携带凭据，但它们和登录表单一样在局域网内明文传输。把入口主机以 TLS 对外发布可一并解决。

**注册页面上写着共享默认密码。** 这是有意的——申请人必须知道自己用什么登录，而现有通道里没有任何经过验证的成员邮箱可用于逐个投递。这使首次登录成为共享秘密而非私人秘密，也正因如此同一个改动里必须有 `/password`。

**令牌有效期与待审批表都不需要清理器。** 未使用的链接会相对于 `created_at` 自然过期，行保留用于审计；`dsh_registrations` 每来一个申请长一行，因此没有做回收路径。
