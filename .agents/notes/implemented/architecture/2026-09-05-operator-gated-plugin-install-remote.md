# Agent Note: The WebUI installs plugins into its own profile through an operator-gated Remote

Status: implemented

English | [中文](2026-09-05-operator-gated-plugin-install-remote.zh.md)

## Problem

[`dsh plugin install`](../../../../apps/cli/src/plugin.ts) installs plugins only from a terminal: it copies a source directory into the profile or runs `pnpm add`, then writes the durable profile files the running instance loads. The web GUI reads that same profile through the read-only [`pluginInventory` projection](2026-08-29-plugin-inventory-agent-preset-scopes.md), but nothing on the web plane can install — a GUI operator asking for a plugin is told to leave the app and open a shell. Closing that gap means exposing an install call on the running instance, and that call writes to the very profile the instance composes itself: copies directories, edits `cordis.patch.yml`, runs `pnpm add`, and rewrites `dsh.profile.bundles`. A namespace that can do that must never be reachable by default, and its failures must say what the operator can fix.

## Decision

**A new host package `@deepseek-ai/dsh-host-plugin-install` exposes one Remote method on a `pluginInstall` namespace.** `PluginInstallGateway extends TypertRemoteService`, is injected with the `loader`, and answers `installPlugin(spec)` over `('installPlugin')` — the [remote method surface](../../../../packages/api/remotes/README.md) a GUI tab registers against in Phase 4. The namespace is mounted into the web-app composition and reaches the client through the api remotes `$mount` list, mirroring how `pluginInventory` travels. Nothing model-facing is registered: the install call is a profile mutation an operator triggers, not a capability the agent loop calls.

**The operator gate is the composition row, and the service double-checks it.** The web-app `cordis.patch.yml` row mounts the package only when `DSH_PLUGIN_INSTALL=true` — a `disabled: !!js` expression evaluated by the [Loader's own disabled interpolation](2026-08-11-loader-entry-disabled-interpolation.md), so a default deploy never loads the code. The service constructor independently throws when its `enabled` config is false, so an embedder that mounts the package without the switch fails loud at load instead of silently serving the namespace. Two layers because they gate different things: composition decides whether the package exists in a deploy; the constructor asserts the deployment meant to expose it.

**The target profile is the running instance's own profile, located two ways.** An explicit `profileDir` config override wins, for tests and embedders that target a foreign directory. Otherwise the service self-locates: the bootstrap `mountRootInclude` pins an `id: 'include'` loader entry whose `config.path` is the profile's `cordis.yml` file URL, and the profile directory is that URL's parent. A deployment with neither fails with a `plugin-install/unknown-profile` RemoteError, never a silent fallback.

**`file-dir` copies a source directory into the profile and registers its patch row.** The source is validated to an absolute existing path and the plugin id to one path-safe segment (letters, digits, `.`, `_`, `-`), so an id can never escape `plugins/`. The directory lands at `profileDir/plugins/<id>/`, replacing a prior copy wholesale, and a `{ "type": "module" }` loose-plugin manifest is written when the copy ships no `package.json` — a name-less marker that keeps a copied directory out of the profile's own bundle manifest. The `- insert:` row naming `file://<profileDir>/plugins/<id>/index.ts` is inserted into `cordis.patch.yml` between `# >>> dsh-plugin-install <id>` and `# <<< dsh-plugin-install <id>` marker comments; a reinstall replaces exactly that block, so every other user row, comment, and `!!js` expression in the file survives byte-for-byte.

**`npm-bundle` runs `pnpm add` in the profile directory and reconciles the layer stack.** A profile without a `package.json` is initialized first via `initProfile`; the package spec is validated non-empty and forwarded to `spawnSync('pnpm', ['add', spec])` with the profile as cwd (shell shim on Windows, matching the CLI). Missing pnpm reports `plugin-install/pnpm-missing`; a non-zero exit reports `plugin-install/pnpm-failed` with the exit code. Success hands the pre-install profile manifest to the [shared `reconcileProfileBundles`](2026-08-05-profile-plugin-bundles.md) — anchored at the profile's own `package.json` as the installation anchor — which promotes `dsh.bundle` packages into `dsh.profile.bundles`; the promoted names come back in the result as `bundlesAdded`.

**Every failure is a `RemoteError` with an actionable message.** The `RemoteErrorDetailsMap` extension in `src/types.ts` owns the closed set: `unknown-profile`, `invalid-spec`, `pnpm-missing`, `pnpm-failed`, `write-failed`. A write failure wraps its cause and says which id and profile directory failed, so a GUI surface can render the message verbatim.

## Alternatives considered

**Reuse the CLI's install code instead of a package.** Rejected. The CLI is an `apps/` entry whose install path mixes pnpm forwarding, a warning stream, and error styling with its command parsing; the host service needs the same durable writes behind a Remote contract, and Phase A keeps the CLI as the shipped authority while the service reuses the shared boot pieces (`initProfile`, `reconcileProfileBundles`, `PROFILE_PATCH_FILENAME`) that commit `11a30687a5` extracted precisely so both callers stay honest.

**Gate only at composition, or only in the constructor.** Either alone left a hole: composition-only lets an embedder mount the package unguarded, constructor-only still loads and parses the namespace in every default deploy. Both layers together make the default deploy provably free of the code and any explicit mount provably intentional.

**Infer the profile from a config value with a silent fallback.** The `mountRootInclude` include entry is where the running instance already records its profile; a hidden `?? default` inside `resolveProfileDir()` would silently install into a directory the instance does not compose. The explicit `profileDir` override exists only for callers that know their target; everyone else must resolve through the composed include entry or fail loud.

**Patch the row by re-dumping the YAML file.** Rejected. `cordis.patch.yml` is a user-edited patch layer holding arbitrary comments and `!!js` expressions; parsing and re-emitting it would rewrite those bytes. The marker-delimited string splice touches only the service's own block, which is the only idempotence the service can claim.

**Validate the install surface against the CLI's behavior.** Deferred to the CLI's own e2e coverage. The service tests pin the durable output (copied tree, manifest, patch block, bundle promotion) and the error vocabulary; the CLI keeps its separate install e2e until the GUI tab (Phase 4) becomes the second consumer worth sharing a contract for.

## Consequences

The web-app bundle gains the operator-gated install row and a dependency on the new package, the api remotes client `$mount`s the namespace, and the config and module-graph catalogs list the new row. A default deployment composes none of it: `DSH_PLUGIN_INSTALL` unset disables the row at composition and the package never loads. When an operator enables it, the GUI can install both a source directory and an npm bundle into the running profile with the same durable writes the CLI produces, and every refusal names what is wrong (`pnpm` absent, a non-path-safe id, an uncomposed include entry). The service keeps no model-facing surface and registers no session events, so no snapshot owns its output; the 15-case spec drives real Loader composition against temp profile fixtures with `spawnSync` mocked for the pnpm path. The GUI settings tab that calls this namespace is Phase 4 of the design document and is deliberately not part of this change.
