# Agent Note：个人 wiki 整体替换层的基线比对冲突守卫

Status: implemented

[English](2026-09-16-wiki-whole-file-write-conflict-guard.md) | 中文

## Problem

[个人 wiki](../feature/2026-09-16-team-shell-user-wiki.zh.md) 的 L1（`.dsh-wiki-identity.md`）和 L2（`.dsh-wiki-preferences.md`）两层按设计在每次 `wiki_note` 调用时整体覆盖写入——沿用 `todo_write` 整表替换的规则。在生产环境中，某用户对同一账号同时运行了两个会话（shadow-pairing 实例和主实例是两个独立的操作系统进程，但共享同一个 workspace，因而共享同一份 wiki 文件的落盘内容）。一个会话在 11:53 写入了 L1；另一个会话手里拿着一份已经过期的内存副本，在 12:55 完全不知道第一次写入的情况下，写入了自己那份完整的 L1，把前一次写入静默地毁掉了。没有任何机制检测或报告这次丢失；用户只是碰巧把文件内容和自己记得写过的东西对比才发现的。`writeWikiLayer` 完全没有"我上次看到磁盘内容时是什么样"的概念，所以任何两个进程在整体替换层上抢跑，都必然让后写者覆盖先写者。

## Decision

**先做快照再在写入时比对，而不是加文件锁。** `writeWikiLayer`（`shell/src/remote/wiki-fs.ts`）为两个整体替换层新增一个可选的 `baseline` 参数。传入该参数时，写入前会先通过新增的 `readWikiLayer` 重新读取磁盘当前内容并与 `baseline` 比对；不一致就抛出 `WikiWriteConflictError`（携带层名和实际的当前内容），而不是直接覆盖。不传 `baseline` 则保留原有的无条件覆盖行为——供给（`ensureUserWiki`）和旧测试仍然依赖这一行为，只有实时工具路径才启用该检查。我们刻意没有加真正的文件锁（例如基于 `mkdirSync` 的互斥锁，用来关闭"读取检查→写入"之间的窗口）：实际生产事故里两次写入相隔了一小时，残余的 TOCTOU 竞态窗口只有微秒级风险，远小于事故的真实窗口，而加锁会带来跨进程清理复杂度（失效锁恢复、崩溃处理），相对这点残余风险不成比例。

**基线保存在进程本地内存中，每个回合都刷新，而不是按 `Agent` 建映射。** `wiki-tool.ts` 维护一个闭包级的 `lastSeen: Partial<Record<WholeReplaceWikiLayer, string>>`，在插件加载时填充一次，并在每次 `agent/pre-step` 钩子最开始（`next()` 之前）再次刷新，因此基线始终反映"这个会话在本回合开始时理应看到的内容"。由于比对目标始终是磁盘上的实时内容——只有"上次看到什么"这一侧存在于内存中——这个设计能够正确检测跨操作系统进程的冲突（正是导致此次事故的 shadow-pairing 与主实例场景），而不仅仅是单进程内部的多个回合。

**冲突以携带最新内容的工具调用失败呈现，而不是静默合并。** `wiki-tool.ts` 的 `execute()` 捕获 `WikiWriteConflictError`，把 `lastSeen` 更新为冲突时的当前内容（这样立即带着合并后的文本重试就能成功，无需再多一次往返），并抛出一个 `Error`，其消息中嵌入了完整的最新磁盘内容以及合并重试的说明。模型把这当作一次可以在同一回合内恢复的普通工具调用失败——没有新工具、没有新协议，也没有让 harness 静默选边的风险。

## Alternatives considered

**在"读取检查→写入"窗口外加一把真正的锁文件（`mkdirSync`/`flock` 式互斥锁）。** 被否决：它关闭的是一个在实际事故中长达一小时的竞态窗口——这不是并发调优问题——同时还带来了自身的失效锁恢复和崩溃安全问题。只有当有证据表明两次写入在实践中确实落在同一个读写窗口内时，才值得重新考虑。

**对两个版本做自动三路合并，而不是暴露一次工具调用错误。** 被否决：L1/L2 是模型对一个人做推理后写出的自由格式文字，不是有安全合并算法的结构化数据；选定一种合并策略会有静默拼出两个写入者都未曾设想的合并文本的风险。把冲突暴露给模型——它本来就以文字形式推理，也掌握自己想写什么的上下文——产生的合并结果比任何机械策略都更贴近本意。

## Consequences

两个会话抢跑同一次整体替换写入时，不再静默毁掉彼此的内容：后写者会收到一次失败的工具调用，附带先写者的内容，并可以在同一回合内合并重试。`shell/tests/wiki-fs.spec.ts` 新增了三个用例（不传基线时无条件覆盖仍然生效；过期基线会抛出 `WikiWriteConflictError` 且不影响并发写入的内容；匹配的基线能成功写入），`shell/tests/wiki-tool.spec.ts` 新增了一个用例（工具层面的冲突变成 `isError: true` 并嵌入另一会话的内容，随后一次合并重试成功）；`wiki-fs`/`wiki-tool`/`spawn-user-wiki` 全套测试（这三个文件共 17 个用例）全部通过，`shell/tsconfig.json` 和 `shell/tsconfig.executor.json` 类型检查均干净。狭窄的"读取检查→写入"竞态窗口按设计仍然存在（见 Decision）；未来若需要关闭它，应该从上面的锁文件方案出发，而不是从头重新论证快照比对。
