# Agent 笔记：挂载根目录自身的 `lstat` 总会被边界检查误判

状态：已实现

[English](2026-09-16-agent-lstat-root-boundary.md) | 中文

## 问题

`shell/src/remote/agent.ts` 的 `runFsOp` 会把每个 `fs:op` 请求与 `session.realRoots`（操作员配置的 `--root` 参数经过 realpath 解析后的结果）做白名单校验。除 `lstat` 外的所有操作都直接调用 `resolveUnderRoot(req.path, session.realRoots)`。而 `lstat` 是先解析 `dirname(req.path)`（父目录），再拼回原样的最后一段，这样才能在请求路径本身是符号链接时报告链接本身，而不是跟随它。

这种基于父目录的检查在 `req.path` 本身就是挂载根目录时必然出错：根目录自身的父目录，天然就在白名单边界之外一层，所以 `resolveUnderRoot(dirname(req.path), realRoots)` 必定抛出 `path outside allowed roots`。`region-router.ts` 的 `lstat()` 覆写正是在这种情形下发出该请求——当 lstat 的 shadow 路径恰好命中一个存活挂载且没有相对子路径时，`remotePath` 就等于 `mount.root` 本身，而这正是对 shadow 根目录做列表/校验时的常见情形。结果就是：只要对挂载根目录本身执行 `lstat`，从这套远程代理架构诞生之初就必然失败，每个挂载都一样。错误信息里用的是未经翻译的 `dirname(req.path)` 原值，读起来像是比配置根目录浅一层的目录缺失，进一步掩盖了真正原因。

## 决定

把解析逻辑抽取为 `resolveLstatTarget(absPath, realRoots)`：先尝试既有的、基于父目录且保留"不跟随"语义的解析；仅当失败原因确系边界检查拒绝了*父目录*路径（错误信息以 `path outside allowed roots` 开头）时，才回退为直接用 `resolveUnderRoot` 解析 `absPath` 本身并探测该结果。回退路径依旧执行同一套白名单——`resolveUnderRoot`——因此不会放行任何本不被允许的路径；它只能弥补基于父目录的方式在结构上无法表达的这一种情形（请求路径本身恰好等于某个根目录)。由于根目录本身是操作员配置的路径而非攻击者可控内容，在这一种"恰好是根目录"的特例里把根目录处的符号链接当作普通文件对待（即跟随它），是可以接受的放宽。

## 考虑过的替代方案

### 为何不直接判断 `absPath === root`，而要捕获特定的错误信息？

依据实际失败方式（边界拒绝）来触发回退，比另行重新推导"路径等于根目录"更可靠；`session.realRoots` 里的 realpath 解析结果，有时与原始请求路径并不字符串相等，即便二者指向同一位置（例如 Windows 盘符大小写不同），单独重新推导等价关系反而可能悄悄漏掉这次要修的正是这种情形。

### 为何不干脆让 `lstat` 始终直接解析 `absPath`，彻底去掉基于父目录的检查？

那样会导致每一次 `lstat` 都跟随最终路径分量上的符号链接，使该操作本应有的语义（报告目标处的链接本身，而非其指向内容）在所有嵌套路径上失效，而不仅是根目录这一种情形。回退逻辑被刻意限定在基于父目录的方式无法表达的这一种情形上。

## 后果

- 对挂载根目录执行 `lstat` 现在可以成功，与从未有过这种不对称问题的 `stat`/`resolve`/`readText` 等操作一致。
- `lstat` 在其他任何路径上的"不跟随符号链接"语义保持不变。
- 真正处于所有白名单根目录之外的路径，在基于父目录的尝试和回退路径中都仍会失败，边界本身未被削弱。
- 回归测试覆盖：`shell/tests/agent.spec.ts` 直接对 `resolveLstatTarget` 做了三项验证：（a）根目录自身的情形，（b）最后一段必须保持原样的嵌套符号链接，（c）真正处于所有根目录之外的路径。
- 这项修复运行在远程代理本身（即配对 Windows 机器上执行的代码）里，而非 dsh 服务端，因此只有在用户重新配对或用更新后的代码重启本地代理进程后才会生效——与本系列前两项仅靠服务端重新部署即可生效的修复不同。
