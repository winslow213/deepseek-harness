# Agent Note: A four-layer personal wiki per account, written by a model-facing `wiki_note` tool

Status: implemented

English | [中文](2026-09-16-team-shell-user-wiki.zh.md)

## Problem

Team-shell gives every account its own isolated `dsh` instance and workspace, but nothing carries durable knowledge about the *person* across sessions: identity facts, working preferences, notable progress, and the reasoning behind past decisions are all lost once a session ends or gets compacted. A user asked for a mechanism where, starting from the first instance a user gets, dsh maintains a personal knowledge model under their workspace and keeps it updated as the conversation produces real breakthroughs — without the user having to write it themselves, and without relying on the model remembering to do so unprompted over a long session.

## Decision

**Four separate files, not one document with sections, split by write semantics and load cost.** `.dsh-wiki-identity.md` (L1, stable facts) and `.dsh-wiki-preferences.md` (L2, working patterns) sit directly at the workspace root and are overwritten whole on every write, mirroring `todo_write`'s whole-list-replace discipline. `.dsh/wiki/timeline.md` (L3, notable progress/breakthroughs) and `.dsh/wiki/decisions.md` (L4, decisions and the alternatives rejected) live under a hidden subdirectory and are append-only — an entry is never rewritten; reversing a decision means appending a new entry that says which earlier one it supersedes, the same never-edit-a-sealed-record rule this repository's own Agent Notes follow. L1/L2 must be direct children of the workspace root specifically because `agent-instructions`'s `localInstructionFileCandidates` walk only checks each directory in the project-root..cwd ancestor chain, never subdirectories — putting them anywhere else would silently stop them from auto-loading.

**L1/L2 piggyback on the existing `agent-instructions` local-overlay mechanism instead of a new context-injection path.** `ensureUserWiki` (called from `provisionUserHome`, so it runs before every instance start, not only at a literal "first ever" boot) upserts an `agent-instructions` config patch adding `.dsh-wiki-identity.md` and `.dsh-wiki-preferences.md` to `localInstructionFileCandidates`. Because that candidate list is checked directly under the project root (which is also the workspace root and the cwd for a team-shell instance), both files load into every turn's baseline context automatically, with zero new plumbing. L3/L4 are deliberately NOT auto-loaded: they are read on demand with the ordinary file tool, avoiding unbounded context growth as the logs accumulate.

**A `wiki_note` tool, not passive end-of-session extraction.** The tool (`shell/src/remote/wiki-tool.ts`) takes a `kind: 'identity' | 'preferences' | 'timeline' | 'decision'` discriminator; the two log kinds additionally accept `alternativesConsidered` (required for `decision`) and `decidedBy`. It is copied — with its pure-fs sibling `wiki-fs.ts`, which has no `@deepseek-ai/*` imports and is shared between the provisioning-time scaffolding and the runtime tool — into `$DSH_HOME/plugins/wiki/` and patched into the account's **home-level** `cordis.patch.yml` (the layer `apps/cli/src/profile-boot.ts` applies after the profile's own patch), not the profile-level patch file `injectRegionRouter` fully overwrites on every call.

**A periodic `<system-reminder>`, modeled on `packages/skill/tool-skill`'s catalog-message injection, counters forgetting.** A process-local `WeakMap<Agent, number>` counts `agent/pre-step` calls; every `reminderEveryTurns` (default 6, configurable) the plugin injects a reminder message and resets the counter, rather than reminding once (the skill catalog's semantics) or never re-nudging over a long session.

## Alternatives considered

**Passive extraction at session-end or compaction time, mirroring `compaction-basic`'s summarizer.** Rejected: a real breakthrough happens mid-conversation and the richest context for describing it exists right then, not after compaction has already discarded detail; a summarizer pass would also cost an extra LLM call per session. The model calling `wiki_note` proactively at the moment of the breakthrough captures more, costs nothing extra when nothing durable happened, and the periodic reminder covers the risk that the model simply doesn't call it unprompted.

**One combined wiki file with sections instead of four files.** Rejected: L1/L2 need "load the whole thing every turn" and L3/L4 need "append forever, never fully reload" — mixing both disciplines in one file forces either parsing/truncation logic that does not otherwise exist, or loading the unbounded logs in full every turn. Four files let L1/L2 reuse `agent-instructions`'s existing local-overlay loading unmodified, and let L3/L4 grow without bound at no per-turn cost.

**Writing the wiki plugin's patch into the profile-level `cordis.patch.yml` `injectRegionRouter` owns.** Rejected: that file is written with a full `writeFileSync` on every `ensureRegionRouter` call (every `provisionUserHome`), so a separate wiki block written there would either be silently wiped on the next region-router refresh or require rearchitecting `injectRegionRouter` into an upsert writer. The home-level patch file already has an established upsert convention (`writeTeamLlmPatch`, `writeTeamSandboxPatch`, `writeTeamDirectoryPickerPatch`) this note's `ensureUserWiki` simply follows.

## Consequences

Every account now gets a personal wiki scaffolded before its first turn, with a tool the model can call to keep it current and a periodic nudge so a long session does not let it go stale. 33 new `node --test` cases across `shell/tests/wiki-fs.spec.ts` (scaffolding and read/write semantics), `shell/tests/wiki-tool.spec.ts` (tool registration, the four `kind`s, required-field validation, and the periodic reminder), and `shell/tests/spawn-user-wiki.spec.ts` (the provisioning wiring end-to-end, including idempotence and preservation of unrelated home-patch content) join the existing shell suite (35 total, all passing); both `shell/tsconfig.json` and `shell/tsconfig.executor.json` typecheck clean, and `wiki-tool.ts`/`wiki-fs.ts` were added to the executor/exclude lists the same way `region-router.ts` and its siblings already are. A future retrieval need beyond "read the file directly" (e.g. searching `decisions.md` by task/session id at scale) is not designed here and should be revisited if the log grows large enough for that to matter. A production incident where two concurrent sessions on one account silently destroyed each other's L1 write led to a conflict guard on the whole-replace layers, documented separately in [the whole-file write conflict guard](../bug-fix/2026-09-16-wiki-whole-file-write-conflict-guard.md).
